# Сессия как дерево тем: дизайн

Заменяет модель `ContextRouter` (≤3 независимых контекста, `.temp/plans/2026-09-12.md`). Не
новая идея — это модель Claude Code: главный разговор порождает фоновые подзадачи, их результат
возвращается в разговор как событие. Мы повторяем её с нуля на Rust.

## Что должен видеть пользователь

Один чат. В нём одна тема в фокусе — с ней идёт диалог. Рядом видны остальные темы сессии: какие
выполняются, какие завершены. Когда фоновая тема завершается, в чат приходит уведомление с её
результатом. Пользователь может переключить фокус на любую тему или начать новую с нуля.

Сценарии, которые модель покрывает без особых случаев:

- первое сообщение содержит одну тему → корневая тема, она в фокусе; по ходу диалога от неё
  ответвляются дочерние;
- первое сообщение содержит несколько тем → несколько корневых тем, одна в фокусе, остальные
  выполняются параллельно;
- фокусная тема завершилась → фокус переходит на следующую незавершённую, вся история сохранена;
- в любой момент можно попросить сводку всего сделанного по сессии.

Голос вне скоупа этого документа: это такой же источник реплик, как текст (см. канало-независимость
в `.temp/plans/2026-09-12.md`), и он вмешивается в диалог тем же механизмом, что и клавиатура.

## Почему не git и не time-travel

Ветки в git — альтернативные версии одного состояния, поэтому им нужен merge с конфликтами. Темы
сессии — разные задачи, идущие параллельно. Результат темы не согласуется с фокусной темой, а
просто становится ей известен. Это поток информации, не слияние состояний; операции «merge» в
модели нет.

Time-travel LangGraph (откат к прошлому checkpoint и повтор) — тоже другая задача. Из LangGraph
берём только субстрат исполнения (checkpoint после каждого super-step, `interrupt`/resume), не
концептуальную модель.

## Модель

### Session

Одна сессия = один append-only лог событий (тот же execution event log, что описан в
`.temp/plans/2026-09-12.md`, раздел 5). В него пишут все темы. Это единственный полный источник
истории: «держим в уме все шаги» означает «всё в логе», а не «всё в prompt».

### Topic

```rust
struct Topic {
    id: TopicId,
    session_id: SessionId,
    parent: Option<TopicId>,      // None — корневая тема
    title: String,                // короткое имя для панели в чате
    status: TopicStatus,          // Queued | Running | Completed | Failed | Cancelled
    execution_id: ExecutionId,    // запуск графа в Engine
    result: Option<TopicResult>,  // заполняется при Completed
}
```

Темы образуют лес: несколько корней, у каждого дочерние. Один `TopicId` в сессии помечен как
`focus`. Фокус — указатель, не свойство темы.

`TopicResult` — это то, что возвращается в фокусную тему: краткий итог (`summary`), ссылки на
артефакты (`artifact_ids`) и `execution_id`, по которому из лога поднимается полная история.
В prompt фокусной темы попадает итог; полная история темы остаётся в логе и доступна по ссылке.
Так «squash» и «полная история» существуют одновременно, и выбирать между ними не нужно.

### Операции

| Операция | Что происходит |
|---|---|
| `create_topic(parent, title, input)` | новая тема; если `parent` = `None` — корневая; стартует Engine-execution; событие `topic_created` |
| `set_focus(topic)` | переставить указатель; событие `focus_changed`; «основная ветка меняется на ответвление» — это она |
| `complete(topic, result)` | статус `Completed`, `result` записан; событие `topic_completed`; результат добавляется в рабочий контекст фокусной темы; в чат — уведомление |
| `fail(topic, error)` / `cancel(topic)` | статус, событие, уведомление; фокус не меняется |
| `restart()` | новая корневая тема, фокус на неё; старые темы не удаляются |
| `summarize_session()` | проекция лога по всем темам; выполняется по запросу, не автоматически |

Лимит одновременно выполняющихся тем — конфигурируемый, по умолчанию 3 (как в прежнем плане).
При превышении новая тема создаётся в статусе `Queued` и стартует, когда освободится слот.
Бюджет и дедлайн на тему — из требований к execution loop в `.temp/goal.md` (раздел 13).

### Маршрутизация реплики

Новая реплика пользователя (текст или транскрипт) идёт в фокусную тему, если:

- пользователь не выбрал явно другую тему в панели;
- реплика не создаёт новую тему.

Является ли реплика новой темой — открытый вопрос из прежнего плана (LLM-классификатор или
правила). Стартовое решение — детерминированное: новая тема создаётся только по явному действию
пользователя (кнопка/команда) или по явной множественности в первом сообщении, которую
выделяет один LLM-вызов на входе в сессию. Автоматическая классификация каждой реплики
откладывается до измерений задержки — ровно как записано в `.temp/plans/2026-09-12.md`.

### Прерывание

Реплика, пришедшая во время выполнения фокусной темы, — это `interrupt` Engine-execution
(субстрат LangGraph: состояние сохраняется в checkpoint, узел при resume выполняется заново с
начала). Клавиатура и голос порождают одно и то же событие `turn_received`; различий в обработке
нет.

## Где это живёт

`TopicManager` — модуль внутри Chat Service, на месте `ContextRouter`. Не отдельный сервис:
Chat уже владеет conversations/messages/streaming, дерево тем — расширение conversation, ровно
по принципу «не плодить Planner/Router-сервисы» из `.temp/plans/2026-09-12.md`.

Engine не меняется концептуально: выполняет один граф на одну тему, как и раньше. Один
`execution_id` на тему; checkpoint после каждого super-step; `interrupt`/resume — как в LangGraph.

Gateway остаётся тонким: проксирует поток событий в клиент.

## События (расширение execution event log)

```text
turn_received     {session_id, channel, turn_id, topic_id}
topic_created     {topic_id, parent, title, execution_id}
topic_queued      {topic_id}                       // лимит слотов
topic_started     {topic_id}
focus_changed     {from, to, reason: user|completion|restart}
topic_progress    {topic_id, message}              // live-status для панели
topic_completed   {topic_id, result_summary, artifact_ids}
topic_failed      {topic_id, error}
topic_cancelled   {topic_id}
notification      {topic_id, kind: completed|failed, text}
```

Все события — тот же append-only лог; отдельного «слоя уведомлений» нет: уведомление — это
событие, которое клиент отображает в чате.

## Контракт для чата

Клиент получает поток событий по сессии и обязан отобразить:

- **транскрипт фокусной темы** — обычный чат;
- **панель тем** — все темы сессии с `title`, `status`, для `Running` — последний
  `topic_progress`; текущий фокус выделен; выбор темы = `set_focus`;
- **уведомления** — `notification`-события рендерятся в транскрипте фокусной темы как отдельные
  сообщения с ссылкой на тему.

Как именно это выглядит (панель сбоку, карточки над полем ввода) — решение фронтенда, спек не
фиксирует. Референс — Claude Code: фоновые задачи как строки статуса, результат — как сообщение
в транскрипте.

## Ошибки

- Падение темы: `Failed` + уведомление; тема остаётся в дереве, фокус не трогаем.
- Падение Chat во время выполнения: темы восстанавливаются из лога (последнее событие по каждой
  теме определяет статус), Engine-executions — из своих checkpoint'ов.
- Реплика в тему со статусом `Completed`: создаётся дочерняя тема от неё с этой репликой как
  входом — прошлое не переписывается.

## Тесты

- `TopicManager` — детерминированный state machine: создание, фокус, лимит слотов и очередь,
  завершение с инъекцией результата, restart, восстановление из лога. Без LLM: fake `LlmClient`,
  как принято в `knowledge-base`.
- Свойство: после любой последовательности операций лог позволяет восстановить дерево тем и
  фокус — это и есть проверка «ничего не потеряно».
- Интеграция с Engine: одна тема = один execution; `interrupt` от новой реплики сохраняет
  состояние и возобновляется.

## Вне скоупа

- Voice Service (STT/TTS) — отдельный план `.temp/plans/2026-09-15-voice.md`.
- Автоматическая LLM-классификация каждой реплики по темам — после измерений.
- Визуальный дизайн панели тем.
- Слияние состояний тем — в модели отсутствует по построению.
