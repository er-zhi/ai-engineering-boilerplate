# Типизированный интент и примитив `race`

Два независимых изменения, которые встречаются в одном турне пользователя:

1. **`race`** — общий примитив «запусти операции, возьми первые N, остальные убей», и
   декларативный тул поверх него, где предмет (погода, акции, курсы) живёт строкой реестра,
   а не Rust-модулем.
2. **Типизированный интент** — первый реальный потребитель `SystemOneService.Decide`
   (TypeSafe AI), уже интегрированного в llm-router, но не вызываемого ни одним сервисом.

Общая цель — мгновенная реакция: один round-trip на решение вместо цикла «подумай → позови
тул → подумай», и отказ ждать медленный источник, когда быстрые уже ответили.

## Контекст: что уже есть

- `SystemOneService.Decide` в `services/llm-router` — `noul` / `choice` / `score`, калиброванные
  вероятности, `confidence`, до 64 вопросов за один провайдерский round-trip. **Ни один сервис
  его не вызывает.** Все четыре потребителя llm-router идут через `Complete` и парсят JSON руками.
- `services/tool/src/tools/web_fetch.rs::fetch_richest` — гонка URL с константой
  `ANSWERS_BEFORE_CHOOSING = 2`. Механика «взять первые N» уже есть, но зашита в один тул и не
  параметризована.
- `d5a8d00` добавлял `weather.rs` / `fx.rs` / `stocks.rs` / `race.rs`, `ee1bd9c` их откатил и
  записал в `.agents/skills/code-review/gate-architecture/SKILL.md` правило
  **«Capabilities, Not Topics»**. Удалённый `race.rs` уже был generic по `T` и по операциям —
  HTTP в нём только в комментарии; не хватало кворума N (брал первый успех) и ширины fan-out.

## Решения, принятые до дизайна

| Развилка | Решение |
|---|---|
| Где живёт предмет («погода», «акции») | Строкой реестра `tool.tools`, не Rust-модулем. Правило гейта «Capabilities, Not Topics» **остаётся в силе и не правится**. |
| Распределение турна между `Decide` и `Complete` | `Decide` всегда, одним вызовом со всеми вопросами. `Complete` — только когда `Decide` сказал «несколько независимых тем». |
| Переспрашивание при отсутствии интента | Chat отвечает сам, шаблонным текстом. Топик не создаётся, Engine не стартует. |
| Роль Knowledge Base | Остаётся обычным тулом каталога (`kb_search`, `kb_read_document`). Модель решает сама. |

## 1. `race` — примитив отмены

Файл: `services/tool/src/race.rs`.

```rust
/// Одна операция: имя для сообщения об ошибке плюс фабрика, стартующая свежую попытку.
pub type OpFuture<'a, T> = Pin<Box<dyn Future<Output = Result<T, String>> + Send + Sync + 'a>>;
pub type OpFn<'a, T> = Box<dyn Fn() -> OpFuture<'a, T> + Send + Sync + 'a>;

pub struct Outcome<T> {
    /// До `take` успехов, в порядке прибытия, с именем давшей их операции.
    pub taken: Vec<(&'static str, T)>,
    /// По одной строке `"имя: причина"` на каждую провалившуюся операцию.
    pub failures: Vec<String>,
}

pub async fn race<'a, T>(
    ops: &[(&'static str, OpFn<'a, T>)],
    fan_out: usize,
    take: usize,
    per_op_timeout: Duration,
) -> Outcome<T>;
```

Свойства, которые обязан иметь примитив:

- **Операции — фабрики, а не готовые футуры.** Отменённую или уже разрешённую футуру нельзя
  опросить повторно, а и резерв, и ретрай требуют свежей попытки. Это же позволяет сложить в
  один `Vec` замыкания разных конкретных типов.
- **`fan_out` — ширина, а не общее число.** Стартуют первые `fan_out` операций; остальные ждут
  в очереди резерва. Как только одна провалилась или истекла по `per_op_timeout`, немедленно
  стартует следующая из резерва, и ширина держится. Это и есть «5 готовых, 3 за раз».
- **`take` — кворум.** Как только собрано `take` успехов, `FuturesUnordered` дропается целиком:
  оставшиеся в полёте операции отменяются на месте, их результаты не ждут и не читают.
- **Возврат всегда `Outcome`, не `Result`.** Частичный успех (`taken.len() < take`, но не ноль)
  — нормальный, а не ошибочный исход: вызывающий сам решает, хватает ли ему одного ответа.
  Пустой `taken` плюс `failures` — это отказ, который называет каждую причину.
- **Ничего про HTTP.** Generic по `T`, ничего не знает ни про URL, ни про reqwest.

Живёт в `services/tool/`, а не в `common/`: гейт разрешает `common` только для кода, **уже**
используемого несколькими сервисами. Переедет, когда появится второй потребитель.

`web_fetch::fetch_richest` переписывается поверх `race` — `ANSWERS_BEFORE_CHOOSING` становится
его аргументом `take`. Внешнее поведение `web_fetch` не меняется: он по-прежнему выбирает из
полученных ответов самую полную страницу, а не самую быструю.

## 2. Декларативный тул: предмет как строка реестра

### Модель

Одна nullable jsonb-колонка `sources` в `tool.tools`. Строка, у которой она заполнена,
исполняется общим декларативным исполнителем, а не Rust-модулем, выбранным по слагу.

```json
{
  "fan_out": 3,
  "take": 2,
  "sources": [
    {"name": "open-meteo",
     "url": "https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lon}&current=temperature_2m",
     "pick": "current.temperature_2m"},
    {"name": "…", "url": "…", "pick": "…"}
  ]
}
```

- `{lat}` подставляется **только** из полей, объявленных в `input_schema` этой же строки, с
  URL-энкодированием значения. Плейсхолдер, которого нет в схеме, — ошибка валидации строки при
  сидировании, а не во время исполнения.
- `pick` — путь по точкам до значения в JSON-ответе источника.
- `ensure_public_url` применяется к каждому **подставленному** URL перед тем, как запрос уйдёт —
  там же, где это делается сейчас: на входе, где появляется недоверенный ввод.
- `timeout_seconds` строки становится `per_op_timeout` гонки.

### Согласование нескольких ответов

При `take: 2` в `Outcome` приходят два значения от разных источников. **Код их не сливает.**
Выход тула — оба значения с именами источников:

```json
{"values": [{"source": "open-meteo", "value": 14.2}, {"source": "…", "value": 14.0}]}
```

Совпали — модель видит подтверждение; разошлись — видит расхождение и может сказать об этом.
Выбор между двумя ценами акции — это суждение, а не арифметика, и делать его в коде значило бы
прятать от модели то, что она обязана знать.

### Сидирование

`weather`, `stock_quote`, `fx_rate` заводятся как seeded строки — тем же путём, что и четыре
нынешних системных тула: `user_id = NULL`, статус `Active` без LLM-ревью, слаг зарезервирован в
`RESERVED_FOR_SYSTEM_TOOLS`. Новый предмет — одна строка, а не деплой.

Конкретные эндпоинты не выдумываются заново: рабочие бесключевые API для всех трёх предметов
уже были подобраны и проверены в `d5a8d00` (`services/tool/src/tools/{weather,fx,stocks}.rs`
до отката) — оттуда берутся URL, пути выборки и единицы измерения, и каждый перепроверяется
живым запросом перед тем, как попасть в сид.

### Почему это не нарушает «Capabilities, Not Topics»

Правило запрещает предмет **в коде**: тул-глагол, никакого `if question.contains("weather")`,
никакого абзаца про один предмет в промпте. Здесь в Rust не появляется ни одного предмета —
появляется одна способность «гонка объявленных источников с подстановкой и выборкой значения».
Предмет живёт там же, где живут пользовательские тулы: строкой реестра. Промпт по-прежнему
ничего не знает ни про погоду, ни про биржи — модель выбирает тул по его `description`, как и
любой другой.

### Что не делается

`CreateTool` **не принимает** `sources`: декларативные тулы сегодня только seeded. Открыть их
пользователям — значит дать произвольный исходящий HTTP по пользовательскому вводу, и это
отдельное решение про SSRF и квоты, а не побочный эффект этой работы. Proto не меняется.

## 3. Интент: один `Decide` на турн

`services/chat/src/classifier.rs` → `services/chat/src/intent.rs`.

### Запрос

`state` — **массив**, не объект. У `google.protobuf.Value` объект это map, и ключи приходят
модели отсортированными по алфавиту; порядок топиков и позиция сообщения потерялись бы. Массив
порядок сохраняет.

```json
[{"topics": [{"id": 7, "title": "…", "status": "running", "focused": true}, …]},
 {"message": "…"}]
```

Вопросы — все в одном вызове (speculative fan-out: второй вопрос дешевле второго вызова):

| id | тип | что решает |
|---|---|---|
| `actionable` | `noul` | `when_true`: есть выполнимый запрос. `when_false`: приветствие, реакция, обрывок — просить нечего |
| `route` | `choice` | по опции `topic_<id>` на каждый живой топик сессии, плюс `new` |
| `separate_themes` | `noul` | сообщение несёт несколько независимых тем |

Опции `choice` — `repeated`, порядок доходит до модели; топики идут в порядке недавности,
сфокусированный первым.

### Как читаются ответы

Пороги — по `confidence`, не по вероятности: `confidence` говорит, различает ли модель варианты
вообще, а вероятность — только какой из них выше. Каждый порог — константа рядом со своим
использованием, с комментарием о цене ошибки.

1. `actionable` уверенно «нет» → событие `CLARIFICATION_NEEDED` в транскрипт, шаблонный текст,
   **топик не создаётся, Engine не стартует**. `SendTurnResponse.topic_ids` пустой.
2. `separate_themes` уверенно «да» → **единственный** вызов `Complete`: разрезать сообщение на
   темы и сочинить `title`/`question` каждой. Существующий промпт классификатора сужается до
   этой одной задачи.
3. Иначе — маршрут по `route`. `new` → один топик, где `question` — **дословный** текст
   пользователя, `title` — его усечение до `MAX_TITLE_CHARS`. Генерация не нужна: правило
   «`question` — это то, что пользователь сам бы напечатал, near-verbatim» уже действует, и
   дословная копия удовлетворяет его лучше любой перефразировки.
4. `route` с низким `confidence` → продолжить сфокусированный топик.

### Что остаётся неизменным

**Классификация остаётся advisory.** Любой сбой `Decide` — недоступный роутер, `unavailable`,
`internal`, вернувшийся `topic_<id>`, которого нет в сессии — падает на существующий fallback:
продолжить сфокусированный топик, а в пустой сессии открыть один топик из самого сообщения.
Турн не теряется никогда.

Новое load-bearing поведение ровно одно — clarification, и оно срабатывает **только** при
успешном `Decide` с уверенным «интента нет». Сбой не переспрашивает: он маршрутизирует как
раньше.

### Протокол

- `ChatEventKind` += `CHAT_EVENT_KIND_CLARIFICATION_NEEDED = 11`.
- `ChatEvent.topic_id` у этого события пустой — событие принадлежит сессии, не топику.
  `payload_json` несёт текст вопроса и `turn_id`.
- `SendTurnResponse.topic_ids` пустой список означает «турн принят, но ни один топик не
  запущен». Поле уже `repeated`, менять его не нужно.
- Фронтенд рендерит событие как реплику ассистента в транскрипте; следующее сообщение
  пользователя идёт обычным `SendTurn` и классифицируется заново.

### Текст переспрашивания — шаблон, не генерация

Сочинять вопрос `Complete`'ом — это второй сетевой вызов на каждом неясном сообщении, ровно на
том пути, который должен быть самым быстрым. Шаблон отвечает за один round-trip.

## 4. Остальные переходы на типизированные запросы

### `services/tool/src/service.rs::validate_tool` → `Decide`

Сейчас: `Complete` с промптом, требующим `{"approved": bool, "feedback": string}`, и ручной
парсинг. `approved` — буквально `noul`. Переходит на `Decide` с одним вопросом; `feedback`
генерируется `Complete`'ом **только при отказе**, то есть редко. На успешном пути один
типизированный вызов вместо одного генеративного с парсингом.

### `services/knowledge-base/src/llm_router_client.rs::enrich` — намеренно не трогается

`page_type` действительно перечисление и просится в `choice`, но `summary` и `keywords`
генеративны. Типизация разрезала бы один вызов на два на **каждом** документе ингеста —
постоянная цена ради типизации одного поля из трёх. Остаётся `Complete`.

### `services/engine/src/executors/llm.rs` — не трогается

Агентный цикл генеративен по своей природе: его выход — либо `tool_call` с произвольными
аргументами, либо текст ответа. `Decide` не генерирует текст. Остаётся `Complete`.

Итого типизируются два места из четырёх, и это весь охват — «где можно», а не «везде».

## 5. Тестирование

**`race`** (модульно, без сети):
- Счётчик в `Drop` у операции-пустышки доказывает, что проигравшие отменены, а не дождались.
- `take = 2` из пяти операций возвращает ровно два значения.
- Провал одной из трёх стартовавших немедленно поднимает четвёртую из резерва — ширина держится.
- Все операции провалились → пустой `taken` и `failures` с причиной каждой.
- Операция, висящая дольше `per_op_timeout`, становится `failure`, а не подвешивает гонку.

**Декларативный тул:**
- Подстановка плейсхолдера с энкодированием; плейсхолдер вне `input_schema` — отказ при сиде.
- `ensure_public_url` отклоняет подставленный приватный адрес до того, как уйдёт запрос.
- `pick` по вложенному пути; отсутствующий путь — ошибка этого источника, не всей гонки.
- Два ответа возвращаются оба, с именами источников.

**Интент:**
- Нужен `FakeSystemOne` в `services/chat/src/fakes.rs` — там сегодня только `FakeLlmRouter`.
- Уверенное «нет интента» → `CLARIFICATION_NEEDED`, ноль топиков, Engine не вызван.
- `separate_themes` → ровно один вызов `Complete`; на всех остальных путях `Complete` не
  вызывается вообще (проверяется счётчиком на фейке).
- Низкий `confidence` у `route` → продолжение фокуса.
- **Существующие тесты на advisory-fallback обязаны остаться зелёными** без правок ожиданий:
  недоступный роутер, мусор вместо ответа, несуществующий `topic_id`.

## Риски

- **`Decide` — один вендор без фолбэка.** У этого класса нет тиров и primary/backup: провайдер
  упал — вызов вернул ошибку. Поэтому advisory-fallback обязателен, а не желателен.
- **Пороги `confidence` подбираются вслепую.** Начальные значения — догадка; их цена
  асимметрична (лишнее переспрашивание раздражает сильнее, чем лишний запуск топика), поэтому
  порог на clarification ставится высоким и снижается по наблюдениям, а не наоборот.
- **`take: 2` удваивает внешние запросы** там, где раньше хватало одного успеха. Это плата за
  видимое расхождение источников; `take: 1` в строке реестра возвращает прежнее поведение без
  изменения кода.
